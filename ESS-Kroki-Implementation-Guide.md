## Part 1: The Embedded Source Schema (ESS) v1.1 Specification

**Goal:** A lightweight, unified XMP namespace to embed generative source payloads directly into rendered assets. Designed for immediate interoperability with Markdown ecosystems and network-efficient transmission.

### 1. Core Properties
*   **Namespace URI:** `http://ns.embedded-source.org/1.0/`
*   **Preferred Prefix:** `ess`
*   **Data Model:** RDF/XML (Standard XMP)

| Property | Type | Requirement | Description |
| :--- | :--- | :--- | :--- |
| `ess:Format` | Text | **Required** | The exact Markdown code block identifier for the engine (e.g., `mermaid`, `plantuml`, `excalidraw`, `diagramsnet`). |
| `ess:Payload` | Text | **Required** | The source code, encoded according to `ess:Encoding`. |
| `ess:Encoding` | Choice | Optional | **Defaults to `gzip+base64`**. Matches standard HTTP/URL transport streams. Can also be `raw`. |
| `ess:Tool` | Text | Optional | The engine/version that rendered the asset (e.g., `kroki/1.3.0`). |
| `ess:URI` | URI | Optional | A link to the remote repository or system where the source is maintained. |

### 2. Physical Embedding Guidelines
*   **PNG:** Embed the XMP XML string into an `iTXt` (International Text) chunk. The chunk keyword *must* be `XML:com.adobe.xmp`.
*   **SVG:** Place the XMP XML block directly inside a `<metadata>` tag as a child of the root `<svg>` element.
*   **PDF:** Embed as an uncompressed metadata stream object within the PDF document catalog.

### 3. Extraction Guide (Using exiftool)
Extract the source payload and decode it back to the original diagram text:
```bash
exiftool -b -ess:Payload image.png | base64 -d | gunzip > diagram.mmd
```

## Part 2: Kroki PR Implementation Guide

### 1. Architecture Interception Point
The optimal place to implement this is within the Vert.x gateway, specifically inside or adjacent to `io.kroki.server.service.DiagramHandler` and `io.kroki.server.response.DiagramResponse`. 

Because Kroki already accepts GET requests where the payload is deflated and base64-encoded, you can pass this exact string directly into the `ess:Payload` field without re-encoding it.

### 2. Step-by-Step Implementation Flow

**Step A: Capture the Original Payload**
Inside `DiagramHandler.java` (or your new interceptor), ensure you retain a reference to the `source` payload and the `diagramType` (e.g., mermaid, ditaa).

**Step B: The Vert.x Closure**
When delegating to `diagramService.convert()`, utilize the `.onSuccess()` closure to modify the returned buffer before handing it off to `DiagramResponse`.

```java
// Conceptual implementation in DiagramHandler.java
diagramService.convert(source, format, options)
    .onSuccess(buffer -> {
        // 1. Construct the XMP Metadata packet
        String xmp = EssMetadataBuilder.build(diagramType, source, "gzip+base64");
        
        // 2. Inject based on format
        Buffer finalBuffer = FormatInjector.inject(buffer, format, xmp);
        
        // 3. Send to user
        DiagramResponse.end(response, source, format, finalBuffer, options);
    });
```

**Step C: Format Injectors**
Create utility classes to handle the byte manipulation:
*   `SvgInjector`: Convert buffer to string, insert `<metadata>{xmp}</metadata>` before `</svg>`, convert back to buffer.
*   `PngInjector`: Parse PNG chunks. Insert an `iTXt` chunk with keyword `XML:com.adobe.xmp` right before the `IDAT` or `IEND` chunk.

### 3. PR Scope & Advantages
*   **Zero Companion Changes:** You do not need to modify the Mermaid, Excalidraw, or PlantUML containers.
*   **Low Memory Footprint:** The buffer interception happens fully asynchronously in memory.
*   **Immediate Value:** Every diagram generated by Kroki instantly becomes a self-contained, editable artifact.
