# SVG ESS Implementation for Kroki - Detailed Plan

## Overview
This document outlines the detailed implementation plan for adding Embedded Source Schema (ESS) support to Kroki, focusing on **SVG output only** for the initial implementation. The feature will embed the original diagram source code as XMP metadata within generated SVG files.

## Scope
- **Format**: SVG output only
- **No Infrastructure Changes**: Minimal modifications to existing codebase
- **Scope**: Inject ESS metadata into SVG files generated by Kroki
- **Encoding**: Use `gzip+base64` as default (matching Kroki's existing URL encoding)

---

## Part 1: Technical Analysis

### Current Kroki Architecture
Kroki is built on:
- **Backend**: Vert.x (Java) gateway server
- **Diagram Processing**: Delegates to external services (Mermaid, PlantUML, Excalidraw, etc.)
- **Response Handling**: `DiagramHandler.java` and `DiagramResponse.java`
- **Format Support**: PNG, SVG, PDF (and others)

### SVG Metadata Injection Points
SVG supports XMP metadata via `<metadata>` tags placed within the root `<svg>` element:
```xml
<svg xmlns="http://www.w3.org/2000/svg">
  <metadata>
    <rdf:RDF xmlns:rdf="http://www.w3.org/1999/02/22-rdf-syntax-ns#"
             xmlns:ess="http://ns.embedded-source.org/1.0/">
      <rdf:Description rdf:about="">
        <ess:Format>mermaid</ess:Format>
        <ess:Payload>H4sIAAAAAAAC/...</ess:Payload>
        <ess:Encoding>gzip+base64</ess:Encoding>
        <ess:Tool>kroki/1.0.0</ess:Tool>
      </rdf:Description>
    </rdf:RDF>
  </metadata>
  <!-- actual SVG content -->
</svg>
```

### Implementation Strategy
1. **Minimal Code Addition**: Create a single utility class `SvgEssInjector.java`
2. **Interception Point**: Modify SVG response handler to call the injector
3. **No Dependencies**: Use only Java standard library (no new Maven dependencies)
4. **No Changes to Diagram Engines**: Kroki's Docker containers remain untouched

## Part 2: Detailed Implementation Steps

### Step 1: Create `SvgEssInjector.java`
**Location**: `src/main/java/io/kroki/server/utils/SvgEssInjector.java`

**Responsibilities**:
- Accept SVG content (as String), diagram type, and original source payload
- Generate ESS XMP metadata block
- Inject metadata into SVG between opening `<svg>` tag and content
- Handle edge cases (malformed SVG, empty content)

**Method Signature**:
```java
public static String injectEssMetadata(
    String svgContent, 
    String diagramType, 
    String sourcePayload
)
```

**Algorithm**:
1. Create XMP metadata block as String with ESS properties
2. Find the first `>` after `<svg` to identify end of opening tag
3. Insert metadata block immediately after opening tag
4. Return modified SVG

**Key Considerations**:
- Use `gzip+base64` encoding by default
- Extract Kroki version for `ess:Tool` property
- Handle already-present metadata gracefully (skip injection if detected)
- Ensure valid XML/RDF structure

### Step 2: Create Metadata Builder Utility
**Location**: `src/main/java/io/kroki/server/utils/EssMetadataBuilder.java`

**Responsibilities**:
- Build properly formatted XMP RDF/XML string
- Handle encoding selection
- Include tool version information

**Method Signature**:
```java
public static String buildXmpMetadata(
    String diagramType,
    String encodedPayload,
    String encoding
)
```

**Output Format**:
```xml
<metadata>
  <rdf:RDF xmlns:rdf="http://www.w3.org/1999/02/22-rdf-syntax-ns#"
           xmlns:ess="http://ns.embedded-source.org/1.0/">
    <rdf:Description rdf:about="">
      <ess:Format>{diagramType}</ess:Format>
      <ess:Payload>{encodedPayload}</ess:Payload>
      <ess:Encoding>{encoding}</ess:Encoding>
      <ess:Tool>kroki/{VERSION}</ess:Tool>
    </rdf:Description>
  </rdf:RDF>
</metadata>
```

### Step 3: Modify SVG Response Handler
**Location**: Identify and modify the SVG-specific response handler

**Changes**:
- After diagram generation succeeds, check if format is SVG
- Call `SvgEssInjector.injectEssMetadata()` on the SVG content
- Return modified SVG to client

**Integration Point** (Pseudo-code):
```java
if (format.equals("svg")) {
    String svgContent = buffer.toString(StandardCharsets.UTF_8);
    String svgWithEss = SvgEssInjector.injectEssMetadata(
        svgContent, 
        diagramType, 
        sourcePayload
    );
    buffer = Buffer.buffer(svgWithEss.getBytes(StandardCharsets.UTF_8));
}
```

### Step 4: Extraction Verification
Users should be able to verify with:
```bash
# View XMP metadata
exiftool image.svg

# Or directly inspect the SVG
grep -A 20 "<metadata>" image.svg | grep -A 20 "ess:Payload"
```

## Part 4: Testing Strategy

### Unit Tests
1. **Test metadata generation**:
   - Valid XMP creation
   - Proper RDF namespace declaration
   - ESS property formatting

2. **Test SVG injection**:
   - Inject into valid SVG
   - Verify metadata placed correctly
   - Preserve original SVG content integrity
   - Handle edge cases (no closing tag, multiple svg elements)

3. **Test with real diagrams**:
   - Mermaid → SVG with ESS
   - PlantUML → SVG with ESS
   - Verify extraction works

### Manual Verification
```bash
# Generate diagram with ESS
curl -X POST 'http://localhost:8080/mermaid/svg' \
  -d 'graph LR; A --> B' \
  --output diagram.svg

# Verify metadata is present
grep "ess:Payload" diagram.svg

# Extract and decode
exiftool -b diagram.svg | grep -A 1 "ess:Payload"
```

## Part 5: Integration Points

### Where to Modify
1. **DiagramHandler.java** (or equivalent):
   - After successful diagram generation
   - Before sending response to client
   - Check format type

2. **DiagramResponse.java** (or equivalent):
   - Add format-specific response logic
   - Call `SvgEssInjector` for SVG format

### What NOT to Change
- Diagram engine integrations (Mermaid, PlantUML containers)
- Response headers or status codes
- URL parameter parsing
- Internal diagram conversion logic
